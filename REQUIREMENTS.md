# LeadFlow — бизнес-требования к MVP

## 1. Идея продукта

LeadFlow — небольшая система для сбора и обработки заявок клиентов малого бизнеса.

Система должна позволять компании:

- принимать заявки с сайта;
- не терять обращения клиентов;
- сразу уведомлять менеджера о новой заявке;
- хранить все заявки в одном месте;
- отслеживать текущий статус каждой заявки;
- видеть базовую историю работы с клиентом.

Типичный пользователь системы — небольшая компания или частный специалист, который получает обращения через собственный сайт.

Примеры бизнеса:

- ремонт и строительство;
- мебель на заказ;
- автосервис;
- юридические услуги;
- разработка сайтов;
- установка оборудования;
- обучение;
- бытовые услуги.

---

# 2. Основная бизнес-проблема

У малого бизнеса заявки с сайта часто:

- приходят только на email;
- теряются;
- обрабатываются с задержкой;
- не имеют единого статуса;
- невозможно понять, какие заявки уже обработаны;
- невозможно посмотреть историю обращений.

LeadFlow должен превращать обычную форму обратной связи на сайте в простую систему управления входящими клиентскими обращениями.

---

# 3. Основной бизнес-сценарий

Клиент заходит на сайт компании.

На сайте он видит описание услуг и форму:

- имя;
- телефон;
- email;
- интересующая услуга;
- комментарий.

Клиент отправляет форму.

После отправки:

1. заявка сохраняется в системе;
2. заявке присваивается статус «Новая»;
3. менеджер получает уведомление в Telegram;
4. менеджер может открыть административную часть системы;
5. менеджер видит новую заявку;
6. после связи с клиентом менеджер меняет её статус.

Пример жизненного цикла заявки:

`Новая → В работе → Выполнена`

или:

`Новая → В работе → Отказ`

---

# 4. Пользователи системы

## Клиент

Посетитель сайта.

Может:

- ознакомиться с услугами;
- заполнить форму;
- отправить заявку.

Клиенту не требуется регистрация.

## Менеджер

Сотрудник компании.

Может:

- авторизоваться;
- видеть список заявок;
- открывать заявку;
- видеть контактные данные клиента;
- менять статус заявки;
- добавлять комментарии;
- фильтровать заявки.

## Администратор

На этапе MVP администратор может обладать теми же возможностями, что и менеджер.

В дальнейшем возможно добавить управление пользователями и настройками системы.

---

# 5. Карточка заявки

Каждая заявка должна содержать:

- уникальный идентификатор;
- имя клиента;
- телефон;
- email;
- выбранную услугу;
- комментарий клиента;
- дату и время создания;
- текущий статус;
- источник заявки;
- внутренний комментарий менеджера.

Пример:

Имя: Иван Петров  
Телефон: +7 999 123-45-67  
Email: ivan@example.com  
Услуга: Разработка сайта  
Комментарий: Нужен сайт для строительной компании  
Источник: Сайт  
Статус: Новая  
Дата: 31.08.2026 15:40

---

# 6. Статусы заявки

Для MVP достаточно следующих статусов:

- Новая;
- В работе;
- Выполнена;
- Отказ.

При создании заявки автоматически устанавливается статус:

`Новая`

Менеджер может изменять статус вручную.

---

# 7. Список заявок

Менеджер должен видеть общий список заявок.

Для каждой заявки в списке отображаются как минимум:

- имя клиента;
- телефон;
- услуга;
- дата создания;
- статус.

Менеджер должен иметь возможность открыть отдельную заявку.

---

# 8. Фильтрация

В MVP необходимо предусмотреть возможность посмотреть:

- все заявки;
- новые;
- находящиеся в работе;
- выполненные;
- отклонённые.

Желательно также предусмотреть сортировку по дате создания.

---

# 9. Уведомления Telegram

При поступлении новой заявки менеджер должен автоматически получать сообщение в Telegram.

Пример уведомления:

Новая заявка

Имя: Иван  
Телефон: +7 999 123-45-67  
Услуга: Разработка сайта

Комментарий:
Нужен лендинг для компании.

Telegram используется как внешний канал уведомления.

Неудачная отправка уведомления не должна приводить к потере самой заявки.

---

# 10. Лендинг

В рамках проекта должен существовать простой демонстрационный сайт компании.

Его задача — показать реальный сценарий использования системы.

Лендинг должен содержать:

- название/описание условной компании;
- несколько услуг;
- призыв оставить заявку;
- форму отправки заявки.

Сложный дизайн и полноценный корпоративный сайт не являются целью проекта.

Главная задача лендинга — служить источником заявок для LeadFlow.

---

# 11. Административная часть

Система должна иметь закрытую часть для менеджера.

После входа менеджер получает доступ к списку заявок.

Из списка можно перейти в карточку заявки.

В карточке можно:

- посмотреть информацию клиента;
- посмотреть комментарий;
- изменить статус;
- добавить внутренний комментарий.

---

# 12. Авторизация

Публичный посетитель сайта не должен иметь доступа к списку заявок.

Только авторизованный сотрудник может:

- просматривать заявки;
- менять их;
- видеть персональные данные клиентов.

Форма создания заявки остаётся публичной.

---

# 13. История изменения статусов

Желательно сохранять историю изменения состояния заявки.

Например:

31.08 15:40 — Новая  
31.08 15:48 — В работе  
31.08 17:10 — Выполнена

Это позволит видеть, как заявка обрабатывалась.

Для первой версии реализации эта функция может быть добавлена после основного CRUD.

---

# 14. Базовая аналитика

После реализации основной функциональности можно добавить небольшой dashboard.

Он может показывать:

- количество заявок всего;
- количество новых;
- количество в работе;
- количество выполненных;
- количество отказов;
- количество заявок за выбранный период.

Дополнительно можно показать распределение заявок по услугам.

Глубокая аналитика в MVP не требуется.

---

# 15. Источники заявок

Для заявки желательно хранить источник.

Например:

- Website;
- Telegram;
- Avito;
- VK;
- Other.

В первой версии реальные интеграции со всеми источниками не нужны.

Достаточно, чтобы заявки с лендинга сохранялись с источником:

`Website`

Это позволит впоследствии расширить систему.

---

# 16. Что НЕ входит в MVP

На первом этапе не требуется:

- полноценная CRM;
- телефония;
- WhatsApp;
- интеграция с Bitrix24;
- интеграция с Avito;
- онлайн-оплата;
- бухгалтерия;
- сложная система прав доступа;
- мобильное приложение;
- real-time чат;
- сложный frontend;
- конструктор сайтов;
- AI-функциональность;
- полноценная маркетинговая аналитика.

Основная задача — законченный небольшой продукт, а не огромная CRM.

---

# 17. Минимально готовая версия

MVP считается рабочим, если можно пройти следующий сценарий:

1. Открыть лендинг.
2. Заполнить форму.
3. Отправить заявку.
4. Заявка сохраняется.
5. В Telegram приходит уведомление.
6. Менеджер входит в административную часть.
7. Видит созданную заявку.
8. Открывает её.
9. Меняет статус на «В работе».
10. Позже меняет статус на «Выполнена».
11. Изменения сохраняются.

Если весь этот сценарий работает — основная бизнес-задача продукта решена.

---

# 18. Цель проекта

Проект должен одновременно быть:

1. демонстрационным .NET-проектом для портфолио разработчика;
2. примером реального клиент-серверного приложения;
3. демонстрацией интеграции со сторонним REST API;
4. примером решения прикладной бизнес-задачи;
5. основой, которую впоследствии можно расширять новыми интеграциями и возможностями.

Главный принцип разработки:

**сначала закончить небольшой рабочий бизнес-сценарий, затем расширять его.**

Необходимо избегать усложнения архитектуры ради самой архитектуры, если оно не требуется текущими задачами продукта.
